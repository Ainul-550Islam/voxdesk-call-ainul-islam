## 1a. Second verification round — the package, applied from scratch

The first round verified a working tree. The second round verified the **package**:
a clean rebuild from the PART 18 v6 artefacts, nothing copied in by hand, the
changeset applied with `patch -p1` on a machine that had never seen this work.

```
$ bash rebuild-fixed-tree.sh --out /var/tmp/base_clean     # 8/8
$ patch -p1 --batch --forward < PART-17B.patch
patch rc=0   rejects=0
$ compare every delivered file with the patched tree → 61/61 identical, 0 differing
$ test ! -e docs/runbooks                                  → old directory gone
$ bash scripts/check_helm.sh                               → PASS (11 checks)
$ bash scripts/sync_chart_alerts.sh --check                → in sync
$ python3 scripts/migrate.py                               → 0095_calls_number_width, 362 tables
$ python3 -m pytest tests/deployment/test_runbook_links.py → 6 passed
```

**A packaging defect this round caught.** The first `PART-17B.patch` I shipped
contained `scripts/bench_pipeline_preamble.py` as a *one-line modification*
rather than a new file — because the baseline tree I diffed against had already
received a copy of it during benchmarking. Applied to a genuinely clean rebuild,
`patch` skipped that hunk: the tree would have come up without the benchmark and
with a `docs/PERF_TUNING.md` §6 referencing a script that does not exist. The
patch in this package is regenerated against a clean rebuild: **70 file sections,
44 of them full additions**, and the apply-verify above is the proof.

Applying the patch **before** the rebuild's post-`pip install` generators is the
clean order. Applying it afterwards also works but leaves three generated files
(`docs/DUE_DILIGENCE/{README,KNOWN_LIMITATIONS}.md`, `evidence/pack/SHA256SUMS`)
with rejected hunks — regenerate them instead (`scripts/repo_stats.py
--write-readme`, `scripts/make_due_diligence_pack.py`) rather than forcing the
patch, and note that the due-diligence pack picks one of two equally stale live
evidence files depending on directory order.

Because the sixth runbook test changes the collected-node count, `docs/STATS.json`
and the derived documents were regenerated in this round: **8,504 collected
pytest nodes** (was 8,503), 1,969 source files, 459,613 physical lines, 1,838
routes, head `0095`.

## 5. Per-call CPU (P17B-06): 39.19 → 14.51 µs/call

`scripts/bench_pipeline_preamble.py`, median of 5×2000 calls, same machine, the
unmodified v6 tree and this tree back to back:

| Run | before | after |
|---|---|---|
| 1 | 39.19 µs | **14.51 µs** |
| 2 | 45.20 µs | **16.65 µs** |
| 3 | 38.43 µs | **13.94 µs** |

≈ **−63 %**, with non-overlapping min/max ranges. `cProfile` named two hot spots
and nothing else: the tool filter's per-schema string work, and a pure locale
lookup running 2–3× per call. Behaviour is pinned by
`tests/agent/test_pipeline_cpu_budget.py` (12 tests) plus the 1 169 existing
agent/telephony tests.

**Not claimed:** that calls got faster. 25 µs per call is 0.25 s of CPU per 10 000
calls. It is on the hot path and it was free; it is not a latency win and the
report in `docs/PERF_TUNING.md` §6 says so in those words.

## 5a. Browser evidence that *was* obtained

Headless Chromium (`chromium-1254`) against the app, real page loads, axe-core
via `@axe-core/playwright`, WCAG 2.0/2.1 A+AA tag set — `scripts/browser_smoke.mjs`,
output in `evidence/browser/2026-11-23/browser_smoke.json`:

| Page | Status | Title | Controls | Nonce CSP present | axe violations |
|---|---|---|---|---|---|
| `/login` | 200 | VoxDesk | 2 inputs, 12 buttons | yes | **0** |
| `/` | 200 | VoxDesk | 14 buttons | yes | **0** |

Zero violations, zero serious, zero critical — matching the `a11y.spec.ts` rule
("zero serious"), on the pages a person sees before they have an account.

**The authenticated journey was attempted twice and did not complete.** Both
attempts are recorded in `evidence/browser/2026-11-23/attempts.json`, with the
kernel's own line:

1. **The real suite** — `npx playwright test e2e/journeys.spec.ts -g "operator can
   sign in"` against the front door. The run is genuine: Chromium opened `/login`
   (200), typed the account's email and password, clicked sign-in, and the request
   came back **502** because the API had just been killed —
   `Out of memory: Killed process … (python3) anon-rss:719880kB`.
2. **A memory-lean script** (`scripts/browser_journey.mjs`: `--single-process`,
   images off, 256 MB JS heap) after pre-compiling every route. The box reached
   38 MB available and the run had to be killed.

Measured footprint of the stack, which is the whole explanation:

| Process | RSS |
|---|---|
| `uvicorn app.main:app` (1 worker, 1 838 routes) | **723 MB peak** |
| `next dev` | 311 MB |
| `chrome-headless-shell` (`--single-process`) | ~200 MB |
| PostgreSQL + Caddy + OS | ~540 MB |

723 + 311 + 200 + 540 > 1 982 MB, and the kernel resolves that by killing the
largest process — always the API. This is not a product defect: in the same
minutes the same API answered `POST /auth/signup` (201) and `POST /auth/login`
(200) over `curl` through the same front door, and pages served in 0.4–1.0 s. It
is why `playwright.config.ts` has **no `webServer` block** and says the suite must
have `docker compose -f docker-compose.prod.yml` up first: the suite needs a host
this sandbox is not.
